# 可行性评估：LLM 企业 Gateway

## 🚩 核心结论

> **结论：条件通过（需修改后重审）** - 项目整体技术方向可行，核心需求（OpenAI协议兼容、RBAC、限流、配额管理）在现有Kotlin+SpringBoot+Redis+MySQL技术栈下均可实现。但存在若干逻辑模糊点、数据架构变更风险及高成本功能点，建议在进入详细设计前与PM逐项确认。

| **研发效能** | 1. **高成本功能点**：流式配额精确扣减、主密钥健康检查、分布式限流均为高开发成本功能，建议MVP阶段简化或延后。<br>2. **低投入高回报**：基础的401/403/429错误返回、虚拟Key生成、简单配额限制在Phase 1实现价值高。<br>3. **Phase分离建议**：将“流式配额扣减”、“多协议原生支持（Gemini/Claude）”移至Phase 2。 | 建议MVP聚焦：**虚拟Key管理 + 基础RBAC + 简单配额限制 + OpenAI V1协议转发（不含流式或流式仅做基本转发）**。 | **低** |

## ❓ 质疑与待确认

> 以下问题需PM进一步明确，否则可能导致后续设计返工：

1. **[严重]** **流式响应中断机制**：`402`或自定义`402`错误块的具体JSON格式是什么？客户端（如Chatbox）如何识别并断开连接？
2. **[严重]** **配额耗尽判断时点**：对于流式请求，是在**发起时**预扣配额，还是在**流结束时**根据真实usage扣减？若采用预扣，中途配额耗尽的处理逻辑同上。
3. **[严重]** **路由策略细节**：虚拟Key到MasterKey的映射，当存在多个可用MasterKey时的权重算法是什么？是否有“团队独立密钥池”优先于“全局密钥池”的设计？
4. **[中等]** **重试与超时策略**：请求转发时的超时时间如何配置？重试仅针对超时还是也包括5xx错误？重试次数上限？
5. **[中等]** **配额重置时间**：团队月度配额统一在每月1日0点重置，还是按团队创建日期计算？
6. **[中等]** **首次登录改密后**：用户是否需要重新登录获取新的Session Token，还是仅更新`password_changed`标志后继续使用当前会话？
7. **[中等]** **计费类型（Free/Paid）**：Phase 1是否真的需要区分Free/Paid模型？目前仅做统计，“免费额度”是否等同于“不扣付费配额额度”？
8. **[低]** **监控仪表盘刷新频率**：PRD要求“每分钟自动刷新”，但未定义数据来源是实时计算还是预聚合？500 QPS下实时聚合成本极高。

## ✅ 可行性评估结论

| 评估项 | 结论 | 说明 |
| :--- | :--- | :--- |
| **业务逻辑完备性** | ⚠️ 需修改 | 流式中断、配额扣减时点、路由策略等核心流程存在定义空白 |
| **技术实现可行性** | ✅ 可行 | 现有技术栈（Kotlin+WebFlux+Redis+MySQL）可覆盖核心需求 |
| **系统稳定性** | ⚠️ 需补强 | 超时降级、主密钥健康检查、Redis降级等需在详细设计中补充 |
| **改造成本** | ✅ 可控 | 无存量业务影响，DDL范围明确，Phase分离可降低单次交付压力 |
| **研发效能** | ✅ 推荐 | MVP范围清晰，低投入高回报点突出 |

**最终建议**：**在PM澄清上述5个严重/中等问题后，可进入详细技术方案设计。** 建议优先聚焦MVP范围（虚拟Key + 基础RBAC + 简单配额 + OpenAI协议转发），将流式配额精确扣减、多协议支持移至Phase 2。
