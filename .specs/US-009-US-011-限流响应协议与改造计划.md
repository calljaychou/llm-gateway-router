# US-009/US-011 限流响应协议与改造计划

## 1. 背景与目标

当前网关限流实现位于 `OpenAiForwardService.tryAcquire(userId)`，采用“固定窗口 + Redis 原子计数”。

现状满足最小可用，但在以下方面存在提升空间：
- 本地限流 429 与上游 OpenAI 429（如 `insufficient_quota`）难区分。
- 限流仅按 `userId` 维度，缺少 `apiKey/model/vendor` 粒度。
- 返回信息较少，不利于客户端自动退避和运维排障。

目标：
- 建立统一的限流响应协议（Header + Body）。
- 形成可灰度的分层限流架构。
- 给出可执行、低风险的分阶段改造路径。

---

## 2. 术语

- **本地限流（Gateway Rate Limit）**：由网关自身策略触发的拒绝。
- **上游限流（Upstream Rate Limit）**：供应商返回的 429 或 quota 超限。
- **Scope（限流作用域）**：`api_key` / `user` / `model` / `vendor` / `global`。

---

## 3. 限流响应协议（草案）

### 3.1 HTTP 状态码

- 限流拒绝统一使用 `429 Too Many Requests`。

### 3.2 Header 规范

所有 429 响应建议返回以下头：
- `Retry-After`: 客户端下次重试建议秒数。
- `X-RateLimit-Limit`: 当前命中策略的总配额。
- `X-RateLimit-Remaining`: 当前窗口剩余配额。
- `X-RateLimit-Reset`: 当前窗口重置时间（Unix 秒时间戳）。
- `X-RateLimit-Scope`: 当前命中的作用域（如 `user`）。
- `X-RateLimit-Source`: `gateway` 或 `upstream`。

### 3.3 Body 规范（OpenAI 兼容扩展）

```json
{
  "error": {
    "message": "Rate limit exceeded for user scope",
    "type": "rate_limit_error",
    "code": "GATEWAY_RATE_LIMIT_EXCEEDED",
    "source": "gateway",
    "scope": "user"
  }
}
```

字段说明：
- `error.code`
  - 本地限流：`GATEWAY_RATE_LIMIT_EXCEEDED`
  - 上游限流：`UPSTREAM_RATE_LIMIT` / `UPSTREAM_INSUFFICIENT_QUOTA`
- `error.source`: `gateway` 或 `upstream`
- `error.scope`: 本地限流建议带上命中维度，便于排障。

---

## 4. 分层限流架构（建议）

### 4.1 层级

- `L1 api_key`：按虚拟密钥限流，隔离同用户多应用场景。
- `L2 user`：按用户总量限流，防止账号滥用。
- `L3 model`：按模型限流，保护热点模型。
- `L4 vendor`：按供应商限流，保护上游通道。
- `L5 global`：全局兜底。

### 4.2 判定顺序

推荐顺序：`api_key -> user -> model -> vendor -> global`，命中即拒绝。

设计原则：
- 优先返回最可操作的限制（通常是 `api_key/user`）。
- 统一输出协议，避免调用方处理分裂。

---

## 5. 与现有代码的对齐点

当前实现关键点：
- `tryAcquire(userId)`：用户维度固定窗口。
- 本地限流通过 `GatewayRateLimitException` 触发 429。
- 上游 429 当前基本透传。

建议在 `OpenAiForwardService` 中新增：
- `RateLimitDecision`：封装 `allowed/retryAfter/scope/limit/remaining/reset/source`。
- `buildRateLimitResponse(decision)`：统一 429 响应构造。
- `mapUpstream429(...)`：把上游 429 归一为协议体并打 `source=upstream`。

---

## 6. 分阶段实施计划（可执行）

### 阶段 A：协议统一（低风险）

目标：
- 不改算法，先统一 429 响应协议和 Header。

改造项：
- 统一本地 429 body 字段（`code/source/scope`）。
- 本地 429 补齐 `X-RateLimit-*` 头。
- 上游 429 增加 `X-RateLimit-Source=upstream`。

验收：
- 第 7 步上游 quota 错误可明确识别为 `source=upstream`。
- 第 8 步本地限流可读到 `Retry-After` + `X-RateLimit-*`。

### 阶段 B：多维限流（中风险）

目标：
- 新增 `api_key/model/vendor/global` 维度，保持可配置开关。

改造项：
- Redis key 规范：`gateway:rl:{scope}:{id}:{bucket}`。
- 策略配置：`application-*.yaml` 增加多维阈值。
- 判定顺序与短路拒绝。

验收：
- 压测可观察到不同 scope 的 429 统计与头字段正确。

### 阶段 C：算法升级（中高风险）

目标：
- 从固定窗口升级为滑动窗口/令牌桶，减少窗口突刺。

改造项：
- 使用 Redis Lua 保证原子读写。
- 灰度开关：`gateway.rate-limit.algorithm=fixed|sliding|token_bucket`。

验收：
- 高并发压测下 429 波动平滑，边界突刺明显下降。

---

## 7. 监控与告警

建议指标：
- `gateway_rate_limit_block_total{scope,source,model,vendor}`
- `gateway_rate_limit_retry_after_seconds{scope}`
- `gateway_upstream_429_total{vendor,code}`

建议日志字段：
- `requestId`, `userId`, `apiKeyId`, `modelAlias`, `vendorId`, `scope`, `source`, `retryAfter`

告警建议：
- 5 分钟 `source=gateway` 的 429 比例异常升高。
- 5 分钟 `source=upstream` 的 `insufficient_quota` 连续触发。

---

## 8. 风险与回滚

- 风险：调用方对新 header/body 的兼容性。
- 控制：阶段 A 先保持旧字段，同时新增扩展字段。
- 回滚：通过配置开关退回旧响应结构与单维限流。

---

## 9. 建议优先级

- P0：阶段 A（协议统一 + 可观测）
- P1：阶段 B（多维限流）
- P2：阶段 C（算法升级）
